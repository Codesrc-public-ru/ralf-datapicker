# PRD — Accessible DatePicker (React/TypeScript)

**Project:** Accessible single-date DatePicker  
**Document version:** 1.0  
**Date:** 2026-04-14  
**Status:** Draft for implementation  
**Primary language:** Russian  
**Target implementation:** React + TypeScript component

---

## 1. Обзор продукта и цели

Нужно разработать переиспользуемый компонент DatePicker для React/TypeScript, ориентированный на:

- выбор **одной** даты;
- соответствие **WCAG 2.1/2.2 Level AA**;
- следование паттерну **WAI-ARIA APG Date Picker Dialog**;
- корректную работу с клавиатурой и скринридерами;
- отсутствие внешних зависимостей, кроме React;
- простую интеграцию в формы и дизайн-систему.

Компонент должен подходить для production-использования в интерфейсах с высокими требованиями к доступности, предсказуемости поведения и качеству UX.

### 1.1 Бизнес-цель

Создать базовый DatePicker, который:

- можно безопасно переиспользовать в нескольких формах и продуктах;
- не требует тяжёлых сторонних библиотек;
- даёт понятный и стабильный API для команд разработки;
- снижает риск accessibility-дефектов и регрессий.

### 1.2 Проблема, которую решает компонент

Обычные DatePicker-компоненты часто:

- плохо работают со скринридерами;
- непредсказуемо ведут себя при ручном вводе;
- ломают фокус при открытии/закрытии;
- не имеют полной клавиатурной навигации;
- плохо интегрируются в controlled-формы;
- перегружены зависимостями.

Этот компонент должен закрыть эти проблемы в рамках MVP.

### 1.3 Цели MVP

MVP должен обеспечить:

1. Выбор одной даты через календарь и ручной ввод.
2. Controlled API через `value` и `onChange`.
3. Поддержку `minDate`, `maxDate`, `disabledDates`, `locale`.
4. Полную клавиатурную навигацию в календарной сетке.
5. Корректное управление фокусом.
6. Корректную озвучку состояний скринридерами.
7. Ошибки ввода и валидации без агрессивного затирания пользовательского текста.
8. Поддержку desktop и mobile без отдельного mobile-mode.

### 1.4 Не цели MVP

В MVP **не входят**:

- выбор диапазона дат;
- быстрый выбор года или прыжки по годам отдельным UI-контролом;
- поддержка uncontrolled-режима;
- выбор времени;
- асинхронная загрузка данных;
- отдельная мобильная версия компонента;
- сложные пресеты дат;
- мультимонтажный popover/portal framework поверх сторонних библиотек.

- нативные `Date` и `Intl` для вычислений и форматирования.

## 3. Целевая аудитория

### 3.1 Основная аудитория

- frontend-разработчики, встраивающие компонент в формы;
- команды дизайн-систем и платформенных UI-компонентов;
- конечные пользователи, которым нужно выбрать дату.

### 3.2 Отдельно важные группы пользователей

- пользователи клавиатуры;
- пользователи скринридеров;
- пользователи с ослабленным зрением;
- пользователи мобильных устройств;
- пользователи, вводящие дату вручную.

### 3.3 Ключевые пользовательские сценарии

1. Выбрать дату через поповер-календарь.
2. Ввести дату вручную в `DD.MM.YYYY`.
3. Очистить выбранную дату.
4. Перемещаться по календарю только клавиатурой.
5. Получить понятную ошибку при невалидном вводе.
6. Понять, что дата недоступна для выбора.

## 4. Scope и основные ограничения

### 4.1 Scope MVP

Компонент предоставляет:

- текстовый input;
- кнопку-триггер открытия календаря;
- popover/dialog с календарной сеткой месяца;
- выбор одной даты;
- ручной ввод;
- очистку значения;
- ограничения по диапазону и списку недоступных дат;
- локализацию интерфейса и озвучивания.

### 4.2 Архитектурные ограничения

- Реализация на **React + TypeScript**.
- Стилизация через **CSS Modules**.
- Без внешних зависимостей, кроме React.
- Датовая математика на нативном `Date`.
- Форматирование и локализация на `Intl`.

### 4.3 Семантические ограничения

Компонент — **strictly date-only**:

- время не отображается;
- время не редактируется;
- сравнение выполняется по календарному дню;
- `Date` используется как технический контейнер даты;
- интерпретация выполняется в локальной таймзоне приложения.

## 5. API компонента

## 5.1 Основной контракт

```ts
value: Date | null
onChange: (value: Date | null) => void
minDate?: Date
maxDate?: Date
disabledDates?: Date[] | ((date: Date) => boolean)
locale?: string
```

### 5.2 Архитектурная модель использования

- Компонент в MVP работает как **controlled-first / controlled-only**.
- Внешнее выбранное значение приходит через `value`.
- Изменение валидного значения передаётся через `onChange`.
- Для ручного ввода используется **внутренний temporary input state**.

### 5.3 Правила controlled-поведения

- Пока пользователь печатает, текст в input может не совпадать с `value`.
- Если текст успешно распарсен и прошёл валидацию, вызывается `onChange(validDate)`.
- Если поле очищено, вызывается `onChange(null)`.
- Если текст невалиден или вне диапазона, `onChange` не вызывается.
- Невалидный текст не затирается автоматически.

### 5.4 Поддерживаемые состояния поля

Компонент обязан поддерживать:

- `disabled`
- `required`
- `readOnly`
- внешнее `invalid` состояние

Состояние `loading` в MVP не поддерживается.

## 6. Функциональные требования

## 6.1 Структура компонента

Компонент должен состоять из следующих частей:

1. **Input** для отображения и ручного ввода даты.
2. **Описание формата** через `aria-describedby`.
3. **Кнопка-триггер** открытия календаря с динамическим `aria-label`.
4. **Dialog / popover** с `role="dialog"` и `aria-modal="true"`.
5. **Calendar grid** как `table[role="grid"]`.
6. Навигационные элементы для смены месяца.
7. Скрытый live region для объявлений смены месяца.
8. Текст ошибки под полем при наличии ошибки.

### Acceptance criteria

- В DOM присутствуют input, trigger, dialog и calendar grid.
- Input связан с описанием формата через `aria-describedby`.
- Trigger имеет динамический `aria-label`.
- Dialog имеет `role="dialog"` и `aria-modal="true"`.
- Календарь представлен как `role="grid"`.

---

## 6.2 Поведение input и ручного ввода

### Требования

- Ручной ввод разрешён.
- Канонический формат ручного ввода для MVP: **`DD.MM.YYYY`**.
- Отображение в input — локализованное.
- Формат должен быть явно объяснён пользователю через `aria-describedby`.
- Частичный ввод разрешён, пока поле находится в фокусе.
- Во время активного ввода компонент не должен преждевременно показывать ошибку.
- `onChange` вызывается только:
  - когда дата полностью валидна;
  - когда поле очищено до `null`.
- Невалидный или out-of-range текст остаётся в поле.
- Пользователь должен иметь возможность удалить дату и вернуться к состоянию `null`.

### Technical considerations

- Нужен внутренний temporary input state.
- Нужна логика синхронизации между внешним `value` и внутренней строкой поля.
- Формат отображения может отличаться от канонического формата ввода, но ожидаемое правило ввода должно быть всегда доступно пользователю.

### Acceptance criteria

- Пользователь может ввести `DD.MM.YYYY` вручную.
- Частично введённая строка не ломает компонент.
- Невалидная строка остаётся в поле после blur.
- При валидной дате вызывается `onChange(Date)`.
- При полном очищении поля вызывается `onChange(null)`.
- При невалидной строке `onChange` не вызывается.

---

## 6.3 Календарь и выбор даты

### Требования

- Компонент поддерживает выбор **только одной даты**.
- Выбор даты возможен:
  - кликом;
  - клавишами `Enter` или `Space` на активной ячейке.
- После выбора даты отдельная кнопка подтверждения не требуется.
- Кнопки `OK` и `Cancel` в итоговом UI отсутствуют.
- Закрытие календаря выполняется через `Escape`, внешний клик или выбор даты.

### Acceptance criteria

- Дата выбирается без дополнительного подтверждения.
- После выбора дата считается установленной сразу.
- Кнопки `OK` и `Cancel` отсутствуют.
- `Escape` закрывает календарь.

---

## 6.4 Клавиатурная навигация

### Требования

Компонент обязан поддерживать:

- стрелки;
- `Home` / `End`;
- `PageUp` / `PageDown`;
- `Shift + PageUp` / `Shift + PageDown`;
- `Enter` / `Space`;
- `Escape`.

### Expected behavior

- Стрелки перемещают фокус между днями.
- `Home` и `End` перемещают фокус внутри недели.
- `PageUp` и `PageDown` переключают месяц.
- `Shift + PageUp` и `Shift + PageDown` выполняют расширенную навигацию, соответствующую принятому APG-поведению.
- `Enter` и `Space` выбирают дату.
- `Escape` закрывает диалог.

### Acceptance criteria

- Пользователь может полностью выбрать дату без мыши.
- Все заявленные клавиши работают предсказуемо.
- После нажатия `Escape` календарь закрывается.

---

## 6.5 Управление фокусом

### Требования

- Внутри dialog должен быть **focus trap**.
- При открытии диалога фокус должен устанавливаться:
  - на выбранную дату;
  - если выбранной даты нет — на сегодняшнюю.
- При закрытии диалога фокус должен возвращаться на кнопку-триггер.
- При повторном нажатии на trigger открытый диалог должен корректно закрываться без «мигания».

### Acceptance criteria

- Фокус не выходит за пределы диалога, пока тот открыт.
- При открытии фокус всегда попадает на ожидаемую дату.
- После закрытия фокус возвращается на trigger.
- Повторное нажатие на trigger не вызывает blur → reopen loop.

---

## 6.6 Доступность и screen reader behavior

### Требования

- Компонент должен соответствовать **WCAG 2.1/2.2 Level AA**.
- Должен ориентироваться на паттерн **WAI-ARIA APG Date Picker Dialog**.
- Trigger должен иметь динамический `aria-label`.
- При фокусе на дате screen reader должен получать полный контекст:
  - день недели;
  - число;
  - месяц;
  - год;
  - статус (например, выбрана / недоступна).
- `aria-selected` должен быть только на выбранной дате.
- Недоступные даты должны быть помечены как недоступные.
- Для озвучивания смены месяца должен использоваться отдельный скрытый `aria-live="assertive"` регион.
- Все `aria-label` и тексты навигации должны локализоваться.
- Ошибочное состояние поля должно отмечаться через `aria-invalid="true"`.
- Сообщение об ошибке и формат должны связываться с input через `aria-describedby`.

### Структурное решение для grid

Допускается реализация, ориентированная на надёжность в браузерах и screen reader связках:

- `td` как контейнер ячейки;
- интерактивный элемент — `button` внутри `td`;
- недоступность может усиливаться нативным `disabled` на `button`.

### Acceptance criteria

- Screen reader корректно озвучивает выбранную и активную дату.
- Смена месяца озвучивается без накопления очереди сообщений.
- Trigger после выбора даты озвучивает обновлённый контекст.
- `aria-invalid` появляется только в ошибочном состоянии.
- Недоступные даты озвучиваются как недоступные.

## 6.7 Локализация

### Требования

- `locale` влияет на:
  - подписи;
  - озвучивание;
  - формат отображения;
  - первый день недели.
- По умолчанию используется **локаль приложения**.
- Названия месяцев, дней недели, `aria-label` и тексты навигации локализуются.

### Acceptance criteria

- При изменении `locale` обновляются текстовые подписи календаря.
- Первый день недели соответствует выбранной локали.
- Озвучивание и навигационные подписи меняются вместе с локалью.

---

## 6.8 Валидация и ошибки

### Требования

- Ошибка показывается текстом под полем.
- Ошибка появляется:
  - на `blur`;
  - после попытки submit формы.
- Во время активного ввода ошибка не показывается слишком рано.
- Показывается **одна приоритетная ошибка за раз**.
- Невалидное или out-of-range значение не затирается автоматически.
- Текст ошибки связывается с input через `aria-describedby`.

### Приоритет ошибок

Приоритет ошибок в MVP рекомендуется зафиксировать так:

1. неверный формат / невалидная дата;
2. дата вне `minDate` / `maxDate`;
3. внешняя ошибка формы;
4. required-ошибка.

### Acceptance criteria

- После blur пользователь видит текст ошибки под полем, если значение невалидно.
- При исправлении значения ошибка пропадает.
- Одновременно отображается только одна ошибка.
- Поле помечается `aria-invalid="true"` в ошибочном состоянии.

---

## 6.9 Ограничения выбора: min/max/disabled

### Требования

- Компонент поддерживает:
  - `minDate?: Date`
  - `maxDate?: Date`
  - `disabledDates?: Date[] | ((date: Date) => boolean)`
- При попытке выбрать недоступную дату:
  - значение не меняется;
  - фокус остаётся на текущей ячейке;
  - отдельная визуальная ошибка не показывается;
  - screen reader должен озвучивать дату как недоступную.
- Если входное `value` находится вне диапазона `minDate/maxDate`, календарь должен:
  - открыть месяц установленной даты;
  - показать соответствующие дни как недоступные;
  - не прыгать на «последний допустимый» месяц.

### Technical considerations

- Сравнение выполняется по календарному дню, а не по timestamp.
- Для `disabledDates: Date[]` нужна нормализация сравнения по дню.
- Для предиката нужен предсказуемый вызов без лишних перерендеров.

### Acceptance criteria

- Даты вне диапазона визуально и семантически недоступны.
- Попытка выбрать недоступную дату не вызывает `onChange`.
- При out-of-range `value` пользователь видит месяц именно этой даты.

---

## 6.10 Визуальные требования

### Требования

- Контраст интерфейса должен быть **не ниже 4.5:1**.
- Состояние фокуса должно быть явно видимым.
- Ячейки дат должны быть одинакового размера.
- Тап-зоны интерактивных элементов должны быть достаточно крупными для mobile.
- Popover/dialog должен адаптироваться по ширине экрана.

### Acceptance criteria

- Контраст проходит проверку инструментами.
- Фокус заметен на клавиатурной навигации.
- Сетка календаря визуально ровная.
- На узких экранах диалог не ломает layout.

---

## 6.11 Мобильное поведение

### Требования

- Отдельного mobile-mode в MVP нет.
- Используется тот же компонент, что и на desktop.
- Popover/dialog адаптируется по ширине экрана.
- Клавиатурная и screen reader логика сохраняется.
- Все интерактивные элементы должны иметь достаточную tappable area.

### Acceptance criteria

- Компонент usable на Safari iOS и Chrome Android.
- Текст, сетка и элементы управления не требуют отдельного mobile UI.
- Основные сценарии доступны на сенсорных экранах.

## 7. Рекомендации по техническому стеку

## 7.1 Рекомендуемый стек

- **React** — базовый UI framework.
- **TypeScript** — строгая типизация API и внутренних состояний.
- **CSS Modules** — изоляция стилей.
- **Native Date** — вычисления, сравнения, календарная логика.
- **Intl** — локализованное форматирование и подписи.

## 7.2 Почему такой стек

- соответствует ограничениям по зависимостям;
- удобен для повторного использования внутри продуктовой кодовой базы;
- прозрачен для аудита и тестирования;
- даёт хороший контроль над accessibility-поведением.

## 7.3 Что важно предусмотреть в реализации

- отдельный слой utility-функций для календарных вычислений;
- отдельный слой форматирования и парсинга;
- слой accessibility-логики отдельно от визуальной части;
- устойчивость к timezone-ошибкам на уровне сравнения по календарному дню.

## 8. Концептуальная модель данных

Так как это UI-компонент, здесь нет серверной БД. Вместо этого фиксируется концептуальная модель данных и состояний.

## 8.1 Внешняя модель

### SelectedDate

| Поле | Тип | Описание |
|---|---|---|
| value | `Date | null` | Выбранная дата |
| minDate | `Date | undefined` | Нижняя граница выбора |
| maxDate | `Date | undefined` | Верхняя граница выбора |
| locale | `string | undefined` | Активная локаль |

### DisabledDatesRule

| Поле | Тип | Описание |
|---|---|---|
| dates | `Date[]` | Набор недоступных дат |
| predicate | `(date: Date) => boolean` | Функция определения недоступности |

## 8.2 Внутренние состояния компонента

### InputDraftState

| Поле | Тип | Описание |
|---|---|---|
| rawInputValue | `string` | Текущий текст в input |
| isDirty | `boolean` | Пользователь менял поле |
| isFocused | `boolean` | Поле в фокусе |
| parsedDate | `Date | null` | Результат парсинга |
| parseError | `string | null` | Ошибка формата/даты |

### CalendarViewState

| Поле | Тип | Описание |
|---|---|---|
| isOpen | `boolean` | Диалог открыт или закрыт |
| visibleMonth | `Date` | Месяц, отображаемый в календаре |
| focusedDate | `Date | null` | Дата, на которой находится фокус |
| selectedDate | `Date | null` | Текущее выбранное значение |
| liveAnnouncement | `string` | Текст для скрытого `aria-live` региона |

### ValidationState

| Поле | Тип | Описание |
|---|---|---|
| isInvalid | `boolean` | Итоговое ошибочное состояние |
| errorType | `'format' | 'range' | 'required' | 'external' | null` | Тип ошибки |
| errorMessage | `string | null` | Текст отображаемой ошибки |

## 9. Принципы UI-дизайна

1. **Предсказуемость:** одинаковые действия дают одинаковый результат.
2. **Ясность:** пользователь понимает формат даты и текущее состояние поля.
3. **Доступность по умолчанию:** a11y — часть базового поведения, а не надстройка.
4. **Минимум лишних шагов:** дата выбирается сразу, без OK/Cancel.
5. **Сохранение пользовательского ввода:** невалидная строка не исчезает внезапно.
6. **Фокус как часть UX:** пользователь всегда понимает, где он находится.
7. **Локализация не только визуальная:** она влияет и на озвучивание.
8. **Mobile-friendly без отдельной ветки UI.**

## 10. Соображения по безопасности

Компонент локальный и не работает с чувствительными данными напрямую, но для него важны следующие меры:

- не использовать `dangerouslySetInnerHTML` для ошибок, подсказок и лейблов;
- не выполнять внешние сетевые запросы внутри компонента;
- не логировать пользовательский ввод в консоль в production;
- не строить логику валидации на небезопасных строковых эвристиках без нормализации;
- не полагаться на timezone-sensitive timestamp-сравнения при date-only логике.

### Дополнительно

Если компонент будет использоваться в форменных библиотеках, нужно избегать утечек несогласованного состояния между внешней валидацией формы и внутренним temporary input state.

## 12. Критерии приемки

Ниже перечислены итоговые критерии приемки MVP.

1. Компонент реализован на React + TypeScript.
2. Используются только React, native Date, Intl и CSS Modules.
3. Поддерживается выбор одной даты.
4. Поддерживается controlled API с `value: Date | null` и `onChange`.
5. Поддерживается ручной ввод в формате `DD.MM.YYYY`.
6. Частичный ввод допускается в фокусе.
7. `onChange` вызывается только на валидной дате или `null`.
8. Невалидный текст не стирается автоматически.
9. Пользователь может очистить поле.
10. Есть input, trigger, dialog и grid.
11. Работают стрелки, Home/End, PageUp/PageDown, Shift+PageUp/Down, Enter/Space, Escape.
12. При открытии фокус встаёт на выбранную дату или сегодня.
13. При закрытии фокус возвращается на trigger.
14. Trigger получает обновлённый локализованный `aria-label`.
15. Смена месяца озвучивается через скрытый assertive live region.
16. Недоступные даты семантически помечены как недоступные.
17. Попытка выбрать недоступную дату не меняет значение.
18. При out-of-range `value` календарь открывает месяц этой даты.
19. Ошибки показываются под полем на blur и после submit.
20. В ошибке выставляется `aria-invalid="true"`.
21. Контраст не ниже 4.5:1.
22. Фокус визуально заметен.
23. Компонент работает на desktop и mobile без отдельного режима.
24. Пройдены unit/integration тесты, axe-core, ручная клавиатурная проверка и SR-проверка.

## 14. Потенциальные проблемы и способы их решения

| Риск | Описание | Способ снижения |
|---|---|---|
| Timezone bugs | `Date` может вести себя как datetime и сдвигать день | Сравнивать только календарный день, документировать date-only semantics |
| Controlled vs input draft conflict | Внешний `value` и внутренний текст могут расходиться | Хранить отдельный temporary input state и чётко определить правила синхронизации |
| SR inconsistencies | Разные screen reader и браузеры по-разному интерпретируют grid | Ручное тестирование на NVDA/VoiceOver, использовать более надёжную структуру с button внутри cell |
| Range validation confusion | Пользователь не понимает, почему дата не выбралась | Помечать дату как недоступную семантически и визуально, не менять значение молча |
| Overeager validation | Слишком ранняя ошибка ухудшает UX | Показывать ошибку на blur и submit, не во время активного набора |
| Focus regressions | Потеря фокуса делает компонент недоступным | Отдельные tests на open, close, Escape, trigger click, focus return |
| Locale edge cases | Разные правила недели и форматирования | Определить `locale` как единый источник подписей, недели и aria-текстов |
| Mobile usability | Слишком мелкие tappable areas | Проверить размеры интерактивных зон и responsive layout |

## 17. Краткая реализационная памятка для инженеров

- Начинать с date-only model, а не с datetime mindset.
- Отделить parsing, formatting и calendar math в независимые utilities.
- Не смешивать selected value и raw input text.
- Не строить a11y как постобработку после UI.
- Сначала покрыть keyboard/focus/screen reader сценарии, потом шлифовать визуал.
- Все критические сценарии должны быть тестируемы и на уровне логики, и вручную.

## 18. Итог

MVP DatePicker должен быть компактным, controlled, доступным, локализуемым и устойчивым к типичным проблемам календарных компонентов: потере фокуса, непредсказуемой валидации, слабой работе со screen reader и timezone-ошибкам.

Критерий успешности MVP: компонент можно безопасно встроить в production-форму без внешней библиотеки дат и без ручного переписывания accessibility-поведения под каждый продукт.
